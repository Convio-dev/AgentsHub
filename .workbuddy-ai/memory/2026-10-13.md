Analyzed the full codebase (~21.6k LOC, .NET 10 WinForms + WebView2, single-file portable exe).

### Architecture map

Helpers: `NetworkHelper`, `StartupHelper` (HKCU\Software\AgentsHub), `ThemeManager`, `QrCodeHelper`, `ShellLauncher`.
External: hermes dashboard, claude, agy, OpenCode sidecar, OpenRouter, LAN devices.

## Fixed: CPU telemetry reading a constant 100%

### Root cause (confirmed in code, not guessed)
`DashboardWebBridge.OnMetricsTimerTick` read `_cpuCounter.NextValue()` into a local `cpuPercent` that was **never used**, then called `GetSystemTelemetryDto()`, which read the *same* delta counter again microseconds later. `% Processor Time` reports the average over the interval since the previous read, so the second read divides by a near-zero interval and yields a bogus value. On top of that, the frontend poll (`get_system_telemetry`, every 2s) and the 2.5s timer push each sampled the counter independently, resetting each other's baseline and producing different numbers for the same instant.

### Changed files
- `Services/DashboardWebBridge.cs` — `_cpuCounter` replaced by a single process-wide `static readonly PerformanceCounter? CpuCounter = CreateCpuCounter()`, primed once with the clock started at prime time. New `SampleCpuPercent()` is the only reader: it returns the cached value while the last sample is younger than `MinCpuSampleIntervalMs` (900ms) **without touching the counter**, otherwise reads and clamps to `[0, 100]`, guarding NaN. `OnMetricsTimerTick` no longer reads the counter (it just posts the DTO). `Dispose` no longer disposes the shared counter.
- `ui/js/dashboard.js` — `handleHardwareMetrics` now sanitizes the CPU value (`cpu` → `cpuPercent` → 0, non-finite → 0), scales a fraction (≤1.0) up to a percentage, clamps to `[0, 100]`, drives the header badge and `cpu-usage-val` from that single `cpuVal`, and computes `maxCpuSeen` as `Math.max(...cpuHistory)` so a transient spike decays out of the window instead of latching Peak at 100% forever.

### Verification
- `dotnet build -c Release` → 0 errors, 0 warnings. `node --check ui/js/dashboard.js` → OK.
- Throwaway harness (reflection into the private `SampleCpuPercent` / `GetSystemTelemetryDto`), 10 assertions, all passing: first sample after priming is 0.0 (no bogus 100), immediate repeat served from cache, four samples at 1.1s spacing read `8.9, 7.4, 5.5, 6.9` against an independent 1s-window reference of `9.5`, and the DTO reports `cpu == cpuPercent == 6.9`.
- Caveat recorded: the legacy double-read reproduced `0.0%` on this machine rather than `100%` — the bogus magnitude depends on timing/core count, but the mechanism is identical and the fix is validated against the independent reference.

## Replaced CPU telemetry with GPU load + a small network load

### Changed / added files
- **New** `Services/HardwareTelemetryService.cs` — background sampler (2s cadence) exposing cached `GpuPercent` and `NetworkKiloBytesPerSec`. GPU = max `Utilization Percentage` across `GPU Engine` instances whose name contains `engtype_3D` and whose embedded pid is still alive (max matches Task Manager's "busiest engine"; summing engines double-counts). Network = sum of `Network Interface` / `Bytes Total/sec` over physical adapters (loopback, tunnel, vEthernet, VMware, VirtualBox, Hyper-V, Bluetooth filtered out). Both counter sets are cached and **reused** across refreshes so the delta baselines survive; the sets refresh every 30s. Results are published into two plain `int` fields (GPU ×10, KB/s) written with `Volatile.Write`, so the UI thread reads a snapshot and is never blocked by a slow pass.
- `Services/DashboardWebBridge.cs` — **all CPU telemetry removed**: the `CpuCounter` static, `CreateCpuCounter`, `SampleCpuPercent`, the cache fields, the `_cpuCounter` dispose line and the dead read in `OnMetricsTimerTick`. `GetSystemTelemetryDto()` now calls `HardwareTelemetryService.EnsureStarted()` and returns `gpu`, `gpuPercent`, `netKbps`, `netMbps` (the `cpu` / `cpuPercent` keys are gone).
- `ui/index.html` — header badge `metric-cpu` → `metric-gpu` (`GPU 0%`), new `metric-net` badge (`NET 0 KB/s`); the CPU tile became a GPU tile (`tile-gpu-metric`, `gpu-usage-val`, `gpu-sparkline-*`, `gpu-grad`, `gpu-stats-sub`, `gpu-engine-sub`) with a GPU icon; new small `net-load-val` chip in the telemetry bottom bar; settings label now reads "GPU, network & RAM resource monitor".
- `ui/js/dashboard.js` — `telemetryState.cpuHistory`/`maxCpuSeen` → `gpuHistory`/`maxGpuSeen`; new `formatNetworkRate()` (KB/s under 1024, else MB/s); `handleHardwareMetrics` sanitises/clamps the GPU value, drives `metric-gpu`, `gpu-usage-val`, `gpu-stats-sub` and `metric-net` + `net-load-val`, and the "High Load" status now keys off GPU.

### Measured cost (why it runs on a background thread)
GPU Engine exposes **455 instances** (143 of them `engtype_3D`, 106 with a live pid). Creating + priming the 3D set costs ~90-100ms and reading it ~54-106ms per pass; the whole first pass takes ~1.1-1.3s because the very first perf-counter category enumeration in a process is slow. Network is cheap (2 counters, ~2ms).

### Verification
- `dotnet build -c Release` → 0 errors, 0 warnings. `node --check ui/js/dashboard.js` → OK.
- Throwaway harness, 16 assertions, all passing: counter sets discovered (106 GPU / 2 network), first pass populated in ~1.1s, GPU readings in `[0, 100]`, network non-negative, counter set stays populated, **10000 cached reads in 0.0ms** (proves the UI thread is never blocked), and the DTO exposes `gpu/gpuPercent/netKbps/netMbps` while `cpu`/`cpuPercent` are gone. Config backed up and restored around the run.
- `assets/web/dashboard.js` / `dashboard.html` and `ui/tabs/*.html` still contain the old CPU markup but are not loaded at runtime; left untouched.
